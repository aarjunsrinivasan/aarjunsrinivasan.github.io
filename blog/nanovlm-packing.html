Packed Sequences Are Leaking Attention in Your Training Run

A nanoVLM worklog: a silent train/inference skew in a widely-read reference repo — how I found it, how I proved it with a test the existing suite couldn't fail, and the one benchmark out of seven that moved.

Sep 2026 16 min read ~25 H100-hours Code, logs & raw data

TL;DR

If you pack several samples into one row and train with plain causal attention, every sample can attend to the unrelated samples before it. Nothing crashes and the loss curve looks normal. At inference the model sees one sample at a time, so you are training it in a regime it never meets at deployment. A second, quieter half of the bug sits in RoPE position ids.

I found both in huggingface/nanoVLM, fixed them, and measured the fix. It made training faster, not slower — FlexAttention skips the masked blocks, so the correct version does less work than the buggy one. It passed one of my two pre-registered loss checks and failed the other. On benchmarks it gave one credible gain out of seven tasks. All of that is below, including the parts that didn't pan out.

Check your own run

  1. Mask: does attention inside a packed row require doc_id[q] == doc_id[kv], or only q >= kv?
  2. Positions: do position ids restart at 0 for each document, or run continuously across the row?
  3. RoPE scaling: does any rotary scaling read position_ids.max() over the packed row rather than over a document?
  4. Tests: if you delete the fix for 1–3, does any test go red? If not, you don't yet know whether the fix is still there.

0Setup and baseline

nanoVLM is a small, deliberately readable vision-language model: a SigLIP2 vision encoder, a pixel-shuffle projector, and a SmolLM2 language backbone. Many people read it to learn how VLM training works, so a bug in it teaches the bug too.

Sequence packing is the most ordinary optimisation in language-model training. Samples are short and the context window is long, so instead of padding every sample to 4,096 tokens you concatenate several into one row. nanoVLM does this with a knapsack packer. It's usually a footnote in a training script, and it's easy to get subtly wrong in a way no error message will ever report.

  • Hardware: 1× H100 80GB, torch 2.14 (cu130), bfloat16.
  • Throughput model: SmolLM2-360M + SigLIP2-base, 460M params, 200-step runs.
  • A/B model: SmolLM2-135M + SigLIP2-base, 228M params, 10,000 steps × 2 arms × 2 seeds.
  • Data and batching: FineVision (streamed), micro-batch 2 × grad-accum 8, rows up to 4,096 tokens.
  • Baseline: packed rows with no document mask, eager, gathered loss. 11,990 tokens/s at 50.3 GiB peak.1

1What goes wrong when you pack

1.1Unrelated samples attend to each other

When you pack samples A, B and C into one row, causal attention lets every token attend to everything before it. That's what causal attention is. But "everything before it" now includes samples A and B, which have nothing to do with C: different images, different questions, different answers.

Upstream's packing didn't mask this. Token 3,000, in the middle of sample C, could attend to sample A's image tokens and sample A's answer.

This isn't a hyperparameter. At inference the model sees one sample at a time, starting from position zero, with nothing before it. So the model is trained in a regime that never occurs at deployment, which is the definition of train/inference skew. The fix is to add one term to the mask:

# FlexAttention: causal AND same-document (models/language_model.py)
def document_mask_mod(b, h, q_idx, kv_idx):
    return doc_id[b, q_idx] == doc_id[b, kv_idx]

mask_mod = and_masks(causal_mask_mod, document_mask_mod, padding_mask_mod)
block_mask = create_block_mask(mask_mod, B, None, T, T, BLOCK_SIZE=128)

1.2The position half, which is easier to miss

Rotary position embeddings encode position, and in a packed row positions run continuously: the third document starts at position 700 instead of 0. Once attention is confined to one document this mostly cancels out, because RoPE scores depend only on relative position (qm·kn is a function of m − n), so a constant per-document offset disappears in the subtraction.

Mostly. nanoVLM's RoPE has dynamic scaling, and it reads the absolute maximum position in the row:

# RotaryEmbedding.forward
max_seq = position_ids.max() + 1        # absolute, across the whole packed row
if max_seq > self.original_max_seq_len:
    inv_freq = self.inv_freq / (max_seq / self.original_max_seq_len)

So packing several short documents can trigger scaling that none of them would trigger alone, and it rescales inv_freq for every document in the row. On a 1,768-token packed row with a 1,024-token backbone context, resetting positions per document matches an unpacked reference to 9.5e-07 (float noise). Leaving them continuous diverges by 3.8e-03, about 40× the test tolerance. The fix restarts position ids at every boundary:

def _compute_reset_position_ids(doc_id):          # [B, T] -> [B, T]
    idx = torch.arange(T).expand(B, -1)
    is_boundary = torch.ones_like(doc_id, dtype=torch.bool)
    is_boundary[:, 1:] = doc_id[:, 1:] != doc_id[:, :-1]
    boundary_idx = torch.where(is_boundary, idx, 0)
    return idx - torch.cummax(boundary_idx, dim=1).values

In nanoVLM's shipped configuration this half is latent rather than live: rows cap at 4,096 and the backbone allows 8,192, so scaling never fires. It goes live as soon as anyone raises the sequence length or swaps in a shorter-context backbone.

Is your setup affected?

  • Affected now if packed rows go through a single causal mask (dense SDPA with is_causal=True, or a [T, T] mask built only from causality and padding).
  • Probably fine on the mask half if you pack through a varlen kernel (e.g. FlashAttention with cu_seqlens), which treats each sequence separately. Still check how your position ids are built.
  • Affected by the latent half if position ids run across the row and anything reads their absolute value: dynamic/NTK RoPE scaling, learned absolute positions, or ALiBi-style biases computed from absolute indices.

2Proving it, rather than asserting it

Saying "attention leaks" doesn't count for much on its own. What counts is a test that fails when the bug is present and passes when it's gone.

2.1A negative control

The first test I wrote perturbs the tokens of document 0 by a large random amount, runs the forward pass, and asserts that document 1's output changes. If documents really leak, it must, and it does. The same probe against the fixed implementations asserts no change. Separately, it checks that positions before any boundary match the unfixed path exactly. That shows the fix is identical wherever leakage was impossible, not just different.

2.2An oracle that doesn't depend on me

The stronger test is this: a packed row must produce the same per-token loss and the same gradients as running each of its documents separately. That's the definition of correct packing, and it doesn't depend on my understanding of the implementation.

2.3Mutation testing: the result that changed my mind

Then I deleted the position-reset call and ran the existing test suite.

All four packing tests passed.

The suite couldn't see the bug. Every existing test ran in a regime where dynamic scaling never fires, which is exactly where continuous positions are harmless. So I wrote three more tests that run in the scaling regime: a backbone context of 32 and documents of 24, 20 and 28 tokens, so only a non-reset packed row crosses the threshold. One of the three is a negative control that asserts continuous positions do produce a mismatch, so the tests can't pass vacuously (9aa6cdb). Against the same mutation, both positive tests now fail.

Mutation testing isn't exotic. You break the code on purpose and see whether anything notices. If nothing does, the tests aren't protecting that code.

3The bug that paid for itself

I implemented the fix two ways: a dense block-diagonal mask that folds doc_id[q] == doc_id[kv] into the SDPA mask, and a FlexAttention BlockMask that expresses the same constraint as block sparsity. On the attention core alone (batch 2, 4,096 tokens, 17 documents per row):

Variant fwd + bwd Peak VRAM
Leaky baseline (no document mask)3.87 ms638 MB
Dense block-diagonal4.10 ms688 MB
FlexAttention, precomputed mask1.92 ms404 MB

The flex path is 2× faster than the buggy version it replaces, with 37% less memory. The dense mask costs 6% because it materialises a full [T, T] boolean matrix, so it pays for correctness that flex gets for free by never visiting the blocks it would have masked. End to end, the 6% disappears into a step dominated by the ViT, the MLPs and the LM head (row 1 of the running table).

Usually correctness costs you speed. You accept the slowdown because wrong answers are worse than slow ones. Here it went the other way. The same information that tells you which blocks to skip is what makes the kernel cheaper, so the bug wasn't buying any speed.

3.1A refusal I had to overturn

The training script refused to combine FlexAttention with whole-model torch.compile. Its stated reason was silent cross-document corruption when compile nests around flex's already-compiled inner calls. That claim needed testing, not trust. I tested it at the real model's dimensions: 32 blocks, 15 query heads, a 1,768-token row whose document boundaries fall mid-block on purpose, and a batch of two rows with different layouts. The BlockMask carries a batch dimension, so a per-row mix-up would be invisible at batch 1. Forward pass and all 290 gradient tensors:

Arm fwd max |diff| vs correct-noise band
Flex + compile4.77e-061.0×
No document mask (negative control)2.94e+00615,872×

The "correct-noise band" matters. Float noise accumulated over 32 layers makes any fixed tolerance arbitrary. So I measured how much two implementations already known to be correct disagree, and checked whether the compiled path sits inside that band. It does.

So the refusal came out, and a test that uses the same geometry went in (e733b77). If a future PyTorch version regresses, that shows up as a failing test instead of a run that silently trains on leaked attention. The refusal may well have been right for the version it was written against. It wasn't right for this one, and measuring was the only way to find out.

4Does it make a better model?

Everything so far is a correctness argument, and a correct model isn't automatically a better one. So I ran two arms, each with two seeds and 10,000 steps, on the 228M model. That took about 25 GPU-hours.

  • Leaky packing: upstream's recipe. No document mask, eager, and the LM head computes logits at every position.
  • Doc-masked packing: FlexAttention document mask with per-document positions, torch.compile, and the LM head computes logits only at the positions that carry a loss. That last change skips logits that were thrown away anyway, so it doesn't change the loss values. It does change memory.

I fixed the decision rule before running anything: the improvement counts only if the gap between arms is larger than the spread between seeds within an arm. It's written down and encoded in the analysis script, so I couldn't quietly revisit it afterwards.

There's a measurement trap here. The two arms disagree about what a batch is. If each arm is scored under its own training mask, you're comparing two different metrics. So every checkpoint of both arms is scored both ways by the same evaluator: per-document (each sample attends only to itself, which is what inference does) and unmasked (the leaky regime). Neither arm gets scored only on its home turf.

Val loss (full val set, mean of 2 seeds) Leaky packing Doc-masked packing Pre-registered check
Scored per-document0.92160.8994gap 0.0222 vs seed spread 0.0134: passes
Scored unmasked0.92010.9147gap 0.0054, inside the 0.0122 spread: fails

One of my two pre-registered checks did not pass. It's also the pattern the hypothesis predicts. The fix should help when the metric matches inference, and it should do nothing under a metric that rewards reading your neighbours' answers. If the unmasked metric had also improved, that would have been harder to explain.

Alongside that, the doc-masked recipe as a whole used 10.1 GiB less peak memory (within 0.1 GiB across seeds) and ran at 1.2–1.7× throughput. These two numbers come from all three changes together, not the mask alone, and most of the memory is not the mask's: of the ~10.1 GiB, about 7.6 GiB comes from the gathered loss alone, with the mask and compile accounting for the rest. Note also that these are not the running table's figures, despite rounding to similar values — the table above is 200 steps at 460M comparing attention paths only (10.4 GiB, 1.70×), while these are 10,000 steps at 228M comparing whole recipes. I'm reporting a range because torch.compile hits its recompile limit on nanoVLM's varying image-tile counts, so the speedup depends on which shapes got compiled before the cap.3

Within a seed, both arms train on byte-identical batches, so they're comparable step for step. The masked arm has the lower per-document loss at 39 of 40 checkpoints. That's a description of how consistent the ordering is, not a significance test.4 The decision comes from the pre-registered rule.

5Watching the leak directly

Loss numbers are indirect. To see the mechanism, I instrumented attention and measured how much softmax probability each token places on keys from earlier, unrelated documents in the row. I computed this per layer and excluded the attention-sink token, which would otherwise dominate.

Layer Leaky-trained model Masked-trained, mask removed Masked-trained, mask removed, positions reset
00.61260.62970.8210
110.16550.24710.9202
250.00280.00940.7702

Two things stand out.

The leaky model had to learn to ignore its neighbours, and only partly managed it. Leakage is heavy in early layers and decays to almost nothing by layer 25. That decay isn't free: it's capacity spent learning something the mask provides structurally. The masked-trained model never had to learn it, and with its mask taken away it attends to neighbours more than the leaky model does at every layer.

The mask and the position reset only work together. The third column is an ablation: the mask is removed but the per-document position reset is kept. Leakage goes up sharply. With continuous positions, earlier documents sit far away in position space, and RoPE's distance decay suppresses them. Reset positions make unrelated neighbours look adjacent. Reset positions without a mask is the worst of the three configurations, which is why the two are gated behind a single flag.5 If you're adding one of them to your own pipeline, add both.

6Downstream: where the good news stops

Validation loss isn't a benchmark. I scored all four final checkpoints on seven lmms-eval tasks, with cluster-bootstrap confidence intervals and Holm correction across tasks. Most importantly, I added a control that measures what changing the training seed alone does to each task. An effect smaller than that control can't be told apart from luck.

That's one credible task out of seven. Six are inconclusive, and one is drifting the wrong way.

ChartQA is the one to look at. It moves −2.84 under seed 0 and +4.84 under seed 1, in opposite directions, and both results have convincing p-values on their own (1.3e-3 and 9.5e-9). Its seed controls are 4.40 and 3.28, which are larger than the effect. With one seed, I would have reported either a solid ChartQA win or a solid regression, with statistics to back it, and I'd have been wrong either way. A second seed prevents exactly that mistake, and it's why six tasks are labelled inconclusive instead of mined for a headline. "Inconclusive" here means undetectable at this minimum detectable effect, not no effect.

There's one question I can't answer. Benchmark inference never packs documents, for either arm, so the leak can't mechanically explain why TextVQA moved. The plausible story is that training under leaked attention gives a weaker model, and the damage concentrates on reading text in images. These numbers are consistent with that story, but they don't prove it.

None of this touches the correctness argument. Cross-document leakage is shown by a negative control and an unpacked-reference oracle. It's a bug whether or not a benchmark moves.

7What this means for your run

  • Check the four items at the top. A packing bug doesn't show up in the loss curve. The only way to find it is to look for it.
  • The fix shouldn't cost you throughput. A block-sparse document mask skips work the leaky version was doing. If your "correct" version is slower, you're probably materialising a dense [T, T] mask.
  • Mask and positions come as a pair. Resetting positions without masking is worse than doing neither.
  • Don't expect a benchmark jump. Here: a clear per-document loss gain, one credible task, and six that two seeds can't resolve.
  • Mutation-test the fix. This suite passed with the bug deliberately put back. Tests that can't fail don't tell you anything.

What I'd do with more compute

Two seeds limit everything above, and a third would help more than any other single run. After that: mark the image count as dynamic so torch.compile stops hitting its recompile limit and the 1.2–1.7× range collapses to one number. I'd also repeat the 200-step component benchmarks, which are single runs in a repo where two runs of one config have differed by 24% across sessions.

The actual lesson

The main takeaway isn't the speedup. It's that the existing test suite passed with the bug deliberately reintroduced.

Tests that can't fail aren't evidence. Neither are benchmarks without a noise floor, or p-values computed over serially correlated checkpoints. The fix itself is just a mask. Most of the work was building measurements I'd have believed if they had told me I was wrong. One of them did, and it's in the table.
