Is Packing Leaking Attention in Your Training Run? A nanoVLM Worklog

A silent train/inference skew in a widely-read reference repo: how I found it, a test my first packing tests couldn't fail, and, in a short 10k-step run, a clear gain on one benchmark out of seven.

Sep 2026 15 min read ~25 H100-hours Code, logs & raw data

TL;DR

VLM training samples vary a lot in length, from a one-line answer to a long document transcription. Padding every sample to the longest wastes most of each batch on pad tokens, so trainers pack several samples into one long row. Done naively, with a plain causal mask and position ids that run on across the row, every sample can attend to the unrelated samples packed before it. Nothing crashes and the loss looks normal, but the model trains in a regime it never sees at inference. huggingface/nanoVLM shipped with exactly this (causal-only attention over the packed row), plus a RoPE position-scaling bug that is latent in the shipped config. I fixed the active attention leak and the latent position issue, tested both fixes, and measured what they bought.

Three checks for your own pipeline

  1. Mask: can a token attend to an earlier, unrelated sample in the same packed row?
    A causal mask alone allows it. You also need a same-sample condition, or a varlen kernel (e.g. FlashAttention with cu_seqlens).
  2. Positions: do position ids restart at 0 for each sample, or run on across the row? If anything reads their absolute value (dynamic RoPE scaling, learned positions), continuous ids are a bug too.
  3. Tests: put the bug back (e.g. delete the position-reset call) and rerun your packing tests. If nothing goes red, your tests don't cover the bug. This is mutation testing; Section 3.2 shows it catching a gap here.

1How nanoVLM packs samples

nanoVLM is a small, deliberately readable VLM (SigLIP2 encoder, pixel-shuffle projector, SmolLM2 backbone) that many people read to learn VLM training, so a bug in it teaches the bug too. It packs short samples into 4,096-token rows instead of padding each one.

The packer is described in Hugging Face's Efficient MultiModal Data Pipeline post. It's a knapsack: it fills each row with samples under a token budget and an image budget, which cuts padding waste. The packer decides which samples share a row. What happens inside the row is up to the model, and that is where upstream nanoVLM had the bug: the whole row ran under a causal-only mask, with position ids counting up continuously from the first sample to the last.

2The bug: packed samples can see each other

2.1Attention crosses sample boundaries

Pack samples A, B and C into one row and causal attention lets every token see everything before it, which now includes A and B: different images, questions and answers. Upstream didn't mask this, so a token in the middle of C could attend to A's image and A's answer.

Upstream's attention call. The only masks are causal and padding, applied to the whole packed row:

huggingface/nanoVLM · models/language_model.py L272–278 (upstream)
is_causal = (T_curr == T_kv and T_curr > 1)
y = torch.nn.functional.scaled_dot_product_attention(
    q, k_exp, v_exp,
    attn_mask=additive_attn_mask,  # padding only
    dropout_p=self.dropout if self.training else 0.0,
    is_causal=is_causal
)

At inference the model sees one sample at a time with nothing before it, so this is train/inference skew. The fix adds one term to the mask. Below is the final FlexAttention version; Section 4.2 covers the dense SDPA mask I tried first.

aarjunsrinivasan/nanoVLM · models/language_model.py L69–95 (fix, simplified)
# FlexAttention: causal AND same-document AND not padding
def document_mask_mod(b, h, q_idx, kv_idx):
    return doc_id[b, q_idx] == doc_id[b, kv_idx]

mask_mod = and_masks(causal_mask_mod, document_mask_mod, padding_mask_mod)
block_mask = create_block_mask(mask_mod, B, None, T, T, BLOCK_SIZE=128)

2.2Position ids and RoPE scaling

In a packed row positions run continuously, so the third document might start at 700 instead of 0. With the mask in place this mostly cancels, since RoPE depends only on relative position. But nanoVLM's RoPE has dynamic scaling that reads the absolute maximum position in the row:

huggingface/nanoVLM · models/language_model.py L87–92 (upstream RoPE)
max_seq = position_ids.max() + 1        # absolute, across the whole packed row
if max_seq > self.original_max_seq_len:
    scale = max_seq / self.original_max_seq_len
    inv_freq = self.inv_freq / scale

So several short documents can together trigger scaling that none would alone, rescaling every document in the row. This is a training-time bug: packing only happens in training, and it fires when the packed row is longer than the backbone's original context (lm_max_position_embeddings), even if every sample in it is shorter. At inference the model sees one sample starting at position 0, so nothing is rescaled. On a 1,768-token row of eight samples with the context set to 1,024, per-document positions match an unpacked reference to 9.5e-07; continuous positions diverge by 3.8e-03, ~40× the 1e-4 test tolerance (small random-weight model on CPU, using the packed-vs-unpacked harness from the tests). The fix restarts position ids at every sample boundary:

aarjunsrinivasan/nanoVLM · models/language_model.py L17–29 (fix, simplified)
def _compute_reset_position_ids(doc_id):              # [B, T] -> [B, T]
    idx = torch.arange(doc_id.size(1), device=doc_id.device).expand_as(doc_id)
    is_start = torch.ones_like(doc_id, dtype=torch.bool)
    is_start[:, 1:] = doc_id[:, 1:] != doc_id[:, :-1]  # first token of each sample
    start = torch.cummax(torch.where(is_start, idx, 0), dim=1).values
    return idx - start                                 # 0, 1, 2, ... within each sample

In nanoVLM's shipped config this half is latent: rows cap at 4,096 and the backbone allows 8,192. It goes live as soon as someone raises the sequence length or uses a shorter-context backbone.

3Testing the fix

A mask that looks right in review proves little. The bug never showed up in the loss, so a wrong fix wouldn't either. I wanted tests that fail when the bug is present, pass when it's fixed, and don't depend on my reading of the code.

3.1Negative control and unpacked oracle

Negative control. Build a packed row with two documents, add large noise to document 0, and run it again. Then compare the output at the last token, which belongs to document 1. On the leaky path that output must change, because document 1 can see document 0. On both fixed paths it must stay identical. The leaky half is what matters: it shows the test can detect a leak at all, so a pass on the fixed paths means something (test).

Oracle. Run each document on its own, unpacked, and compare with the same documents packed into one row. Per-token loss and gradients must match within tolerance. That is the definition of correct packing: it should change throughput, never the math (test). The leaky path fails this check, as it should (test).

3.2Mutation testing found a gap in my own tests

Mutation testing means putting a known bug back into the code and checking that some test fails. I deleted the position-reset call and reran the packing tests I had written for the fix (upstream had none). All four passed.

Every test used rows short enough that RoPE's dynamic scaling never fires, and that is exactly where continuous positions are harmless (2.2). I added three tests that run in the scaling regime: every sample fits the context, the packed row doesn't. Two check that the fixed paths match the unpacked reference; the third is a negative control that turns the reset off and requires a mismatch, so the first two can't pass vacuously. Against the same mutation, both positive tests now fail.

aarjunsrinivasan/nanoVLM · tests/test_vision_language_model_packing.py L273–334 (simplified)
SCALING_MAX_POS = 32
SCALING_DOC_LENS = (24, 20, 28)   # each sample < 32, packed row 72 > 32

def test_rope_reset_keeps_packed_row_out_of_scaling(self):
    assert self._scaling_regime_worst_diff('flex_document_causal') < 1e-4

def test_removing_rope_reset_is_detected(self):   # negative control
    assert self._scaling_regime_worst_diff('dense_block_diagonal', reset_positions=False) > 1e-3

4Speeding up my experiments

Before the long training runs I made each run cheaper. The A/B in Section 5 is four 10,000-step runs, and I was paying for every GPU-hour, so throughput and memory decided how much I could test. None of these changes alter what the model learns; each one is checked against a known-correct reference.

My setup for experiments: a single RunPod GPU instance.

  • Hardware: 1× H100 80GB (RunPod), torch 2.14 (cu130), bfloat16.
  • Throughput model: SmolLM2-360M + SigLIP2-base (460M params), 200-step runs.
  • A/B model: SmolLM2-135M + SigLIP2-base (228M params).
  • A/B runs: Baseline vs Doc-masked (defined in Section 5), 2 seeds each, 10,000 steps per run.
  • Data and batching: FineVision (streamed), micro-batch 2 × grad-accum 8, rows up to 4,096 tokens.
  • Baseline: packed rows with no document mask, eager, gathered loss. 11,990 tokens/s at 50.3 GiB peak.1

4.2Dense mask vs FlexAttention

My first fix was the obvious one: keep SDPA and fold the same-document check into the dense [T, T] mask, the same approach Molmo2 takes for its packed examples. It was correct, but it was the slowest option: it materialises the whole mask and still computes every masked-out block.

FlexAttention's BlockMask expresses the same rule as block sparsity, so fully masked blocks are never visited. On the attention core alone (batch 2, 4,096 tokens, 17 documents per row):

Variant fwd + bwd Peak VRAM
Leaky baseline (no document mask)3.87 ms638 MB
Dense block-diagonal4.10 ms688 MB
FlexAttention, precomputed mask1.92 ms404 MB

Script: eval/benchmark_attn_packing.py · raw numbers: eval/h100/attn_packing.md. Synthetic tensors, no model; 3 warmup + 10 timed iterations.

Flex is 2× faster than the buggy version it replaces, with 37% less memory. The dense mask's 6% cost disappears end to end (row 1 of the table in 4.1). Usually correctness costs speed; here the information that says which blocks to skip is what makes the kernel cheaper.

End to end, the speedup is smaller than the kernel number. Attention is only part of a training step, and torch.compile does most of the work. Rows 3 and 4 of the table in 4.1 have the same mask: dense + compile runs at 1.64×, Flex + compile at 1.70×. That's a 4% gap from single runs, close to the ~2% I treat as a tie. So most of the 1.70× comes from compile, not from Flex. Flex's reliable win is memory: 2.6 GiB less peak than the compiled dense mask (39.83 vs 42.46 GiB). The claim that holds up is the narrow one: the correct mask costs nothing, and the fastest correct path is faster than upstream.

4.3Enabling FlexAttention with torch.compile

The training script refused to combine FlexAttention with whole-model torch.compile, citing silent cross-document corruption. I tested that at the real model's dimensions, with document boundaries falling mid-block and two rows with different layouts in one batch. Forward pass and all 290 gradient tensors:

The compiled path sits inside the noise band of two known-correct implementations, so the refusal came out and a test with the same geometry went in. A future PyTorch regression now shows up as a red test, not a silently leaking run.

    assert_close(grads[name], ref_grads[name], atol=1e-4, rtol=1e-3)

4.4Computing logits only where there is a loss

Upstream computes LM-head logits at every position of the row and then discards most of them, since only answer tokens carry a loss. With a 49k-token vocabulary that logits tensor is large. Selecting the supervised positions before the LM head gives bit-identical loss and gradients, and saves 7.6 GiB of peak memory in the Section 5 runs. The change is one small commit, with an equivalence test. Every row in the 4.1 table already uses it, so that table compares attention paths only.

5Training A/B: Baseline vs Doc-masked

A correct model isn't automatically a better one, so I trained two arms on the 228M model (135M SmolLM2 backbone), two seeds each, 10,000 steps (~25 GPU-hours):

  • Baseline: upstream's recipe. Causal-only packing (no document mask, continuous positions), eager, logits at every position.
  • Doc-masked: Flex document mask + per-document position reset, torch.compile, and logits only where there is a loss.

I use these two names for the trained models from here on. When I change something at eval time only, it gets a suffix: as trained, mask off, or mask off, reset kept.

What else differs between the arms. The Doc-masked arm also has two speed optimisations, and neither changes what is being optimised. Gathering the supervised positions before the LM head gives bit-identical loss and gradients (the commit's test checks it). The compiled Flex path matches known-correct eager implementations to 4.77e-06 (Section 4.3). They change speed and memory, not the loss. Bundling them in let each 10k-step run fit the budget. The intended learning change is document isolation; the bundled optimisations passed loss- and gradient-equivalence checks, though I didn't run an arm that holds them constant over a full training run.

The decision rule was fixed before running anything and encoded in the analysis script: the gap between arms must exceed the seed-to-seed spread within an arm. Every checkpoint of both arms is scored two ways by the same evaluator: per-document (what inference does) and unmasked (the leaky regime), so neither arm is judged only on its home turf.

Val loss (full val set, mean of 2 seeds) Baseline Doc-masked Decision rule (set before the runs)

One of my two decision-rule checks did not pass. That is also what the hypothesis predicts: the fix should help under the metric that matches inference, and not under one that rewards reading your neighbours' answers.

The full Doc-masked recipe also used 10.1 GiB less peak memory (7.6 GiB of it from the gathered loss) at 1.2–1.7× throughput.3 Both arms see byte-identical batches within a seed, and Doc-masked has the lower per-document loss at 39 of 40 checkpoints. That describes consistency, not significance.4

6How much the trained models attend across samples

Loss numbers are indirect. To see the leak itself, I hooked every attention layer of the language decoder (all 30 layers of SmolLM2-135M, 9 heads each; the vision encoder isn't included), ran validation rows through the trained models, and measured the leak mass: how much of each token's attention lands on earlier, unrelated samples in its row.

What this checks. Every run here is an eval-time intervention on the four trained step-10k checkpoints. No new training. Two questions: does Baseline actually use the unrelated context it can see, or does it ignore it? And what did Doc-masked learn about neighbours it never saw? For Baseline the measurement is descriptive: it's how the model already runs. For Doc-masked it's a counterfactual: what its attention would do if the mask were taken away. It shows mechanism, not causes of any benchmark result.

Doc-masked as trained scores exactly 0 by construction, so I ran it two more ways. Mask off removes the mask. One flag controls both the mask and the position reset, so this also switches positions back to continuous. Mask off, reset kept removes only the mask.

Baseline learned to ignore its neighbours, but only in the deeper layers. This was expected. Through layer 10 it puts 40–70% of its attention on other samples, and from layer 11 on it filters them out. That's consistent with the model learning to suppress unrelated context, something a mask would give it for free. The heatmap shows where the leak lives:

The mask and the position reset only work together. I didn't expect this one. With the mask off and the reset kept (green), leakage goes up sharply, to 0.78 at layer 25 against 0.01 without the reset.5 My best guess is RoPE:

That's why the two are gated behind a single flag. One caveat: this is an eval-time result on a model trained with both. I didn't train a model with reset positions and no mask. Still, if you add one to your pipeline, add both.

7Downstream evals with lmms-eval

Lower validation loss doesn't guarantee better task scores, so I ran all four step-10k checkpoints through standard VLM benchmarks. The setup:

  • Harness: lmms-eval, with all four step-10k checkpoints (2 arms × 2 seeds) scored on the same items.
  • Tasks: TextVQA, DocVQA and InfoVQA (val splits), ChartQA, OCRBench, AI2D, ScienceQA. That's 1,000–5,349 items each, with each task's standard metric (ANLS for DocVQA and InfoVQA, relaxed accuracy for ChartQA, exact match or accuracy elsewhere).
  • Statistics: paired per-item differences, 95% cluster-bootstrap CIs (clustered by image or document where known), and Holm correction across tasks. The bootstrap CIs cover uncertainty over evaluation items for these four trained models, not variation between training runs, so I add a control for what changing the training seed alone does to each task. An effect smaller than that can't be told apart from luck.

That's one credible task out of seven: six are inconclusive, and one is drifting the wrong way.

ChartQA shows why the second seed matters. It moves −2.84 under seed 0 and +4.84 under seed 1, each with a convincing p-value on its own, yet its seed controls (4.40 and 3.28) are bigger than the pooled +1.00. With one seed I would have reported a solid win or a solid regression, and been wrong either way. "Inconclusive" means undetectable at this effect size, not no effect.

Benchmark inference never packs, for either arm, so the leak can't mechanically explain TextVQA. The plausible story is that Baseline training yields a weaker model, with the damage concentrated on reading text in images. The numbers fit that story but don't prove it. Either way the correctness argument stands on the negative control and the oracle.

8Takeaways

  • Check the items at the top. A packing bug doesn't show up in the loss curve.
  • The fix shouldn't cost throughput. Even the dense mask tied the leaky baseline end to end here. Most of the speedup came from torch.compile; Flex adds a little speed and a lot of memory headroom.
  • Mask and positions come as a pair. At eval time, removing the mask while keeping reset positions leaks far more than removing both, so gate them together.
  • Don't expect a benchmark jump at this scale. At 228M parameters (135M language backbone) and 10,000 steps, where absolute scores sit at 13–40 points: a clear per-document loss gain, one credible task, and six that two seeds can't resolve. Whether the gap grows with longer training is untested.
  • Mutation-test the fix. This suite passed with the bug put back.

With more compute I'd add a third seed first and train longer, to see whether the downstream gap grows. Then I'd mark the image count as dynamic so torch.compile stops hitting its recompile limit and the 1.2–1.7× range becomes one number.

Main lesson

The main takeaway isn't the speedup. It's that my own packing tests passed with the bug deliberately reintroduced. The fix is just a mask; most of the work was building measurements that could disagree with me. One did: the val-loss check scored without the mask didn't pass (Section 5), as the hypothesis predicts.
